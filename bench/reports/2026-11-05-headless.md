# The bare EQ, headless

This is the first comparison of Seam against plain JUCE, run on the bare EQ with no
editor open. The audio thread's core was kept awake for the main figures. Measured that
way, Seam through JUCE's wrapper (C) takes 6 to 12% less time per block than plain JUCE
(A-native), and Seam's own VST3 build (B) takes 8 to 35% less. That holds at every block
size and in every scenario. A core kept awake is also the warm-cache case, the kindest
to the builds with the larger footprint; with the core asleep between blocks, B's lead
at small blocks grows. The builds that store the same values all play bit for bit
alike. `scripts/compare.py` made the tables below. This overview is written by hand,
after a fairness review of the first version of this report. `2026-11-05-ladder.md`
takes the lead over A-native apart: with the Rust EQ's filters in C++, built by LLVM
inside the same wrapper, plain JUCE is level with C.

## Overview

- **Output.** A, B and C each play the parity script bit for bit as the Rust EQ driven
  directly does. They also match each other bit for bit in every timed run: 324
  comparisons, 236 million samples. A-native, plain JUCE, stores values a little apart
  from Seam's and plays up to -59.6 dBFS RMS and -39.2 dBFS peak apart from A, so it
  is timed but not matched.
- **Time per block, with the core awake (spin).** As a share of A-native's time:
  - With nothing moving, B takes 0.85 to 0.92 and C 0.91 to 0.94.
  - With one parameter moving, B takes 0.83 to 0.91 and C 0.91 to 0.94.
  - With all 18 moving, B takes 0.65 to 0.88 and C 0.88 to 0.94. The gap is widest at
    small blocks: at 32 frames A-native takes 3.07 µs, C 2.72 µs and B 2.00 µs.
  - Every round lies within 3% of its median. A and A-native run the same code when
    nothing moves, and they agree within 1.5%.
  - No build used more than 1.1% of a block's real-time budget, and none overran.
  - A host running many plugins per callback keeps the core awake but evicts each
    plugin's caches between calls, so it sits between these figures and the idle ones.
- **Against A.** A stores exactly what the Rust EQ stores, through a port of Seam's
  ranges: the same arithmetic, which MSVC runs at about 1.4 times Seam's cost here. JUCE
  converts each host write through that port 8 times; Seam converts it twice, and the
  adapter four times. So with every parameter moving A is far slower than plain
  JUCE: at 32 frames it takes 6.48 µs against A-native's 3.07 µs, and B takes 0.31 of A's
  time. That is the cost of the port in JUCE's call pattern, not JUCE's own cost.
  A-native gives the plain-JUCE figure.
- **What each pair separates.**
  - B and C come from the same Rust source, built twice: once as a VST3 module and once
    as a static library behind the C interface. C runs JUCE's VST3 wrapper, the adapter
    and the C interface where B runs Seam's exporter. With nothing moving, C takes 0.05 µs
    a block more at 32 frames, growing to 0.7 µs at 1,024. The growth is probably the wrapper copying each block
    into its own buffer and back, where Seam's exporter works in place. That reading
    comes from the code; it was not measured on its own.
  - A-native and C both run inside JUCE's wrapper, so the gap between them is the plugin
    side. Seam's parameters, the Rust filters, the adapter and the C interface stand
    against JUCE's `AudioProcessorValueTreeState` and its `dsp::IIR` filters, built by
    different compilers. C takes 0.88 to 0.94 of A-native's time in every scenario. This
    run does not separate the compiler from the framework.
- **With the core asleep (idle).** Here the audio thread sleeps between blocks, as in a
  light session.
  - Small blocks cost more for every build: at 32 frames with nothing moving, A-native
    takes 1.02 µs against 0.79 µs with the core awake.
  - Up to 256 frames B takes 0.64 to 0.85 of A-native's time, and its lead grows when
    the core sleeps: at 32 and 64 frames its ratios are 0.07 to 0.12 below the spin ones.
    C takes 0.90 to 0.98, but in 4 of these 12 cells its rounds overlap A-native's. The
    gauge for that is A against A-native, the same code when nothing moves, which differ
    by up to 4% at these sizes.
  - At 512 and 1,024 frames the idle figures are noise, and those rows rank nothing. A
    and A-native run the same code when nothing moves, yet differ there by up to 37%.
  - How deeply the core sleeps varies with the machine's state. An earlier run of the
    same builds, whose data is kept beside this report, saw 32-frame blocks take 3.6 µs
    in two rounds and 1.1 µs in the third, with every build moving alike.
- **Outside `process`.** With nothing moving, the host process spends more cycles on B
  and C than on A:
  - B: 4 to 7 million a second more on the main thread, from its window timer, which
    fires every 15 ms.
  - C: about 3 million more on the main thread and 4.6 to 6.5 million more on other
    threads. That is its 60 Hz tick on a `juce::Timer`: the timer thread of C's own copy
    of JUCE posts it, and the tick runs on the main thread.
  - At the counter's 4.69 GHz that is about 0.1% of one core for B and 0.2% for C.
  - With parameters moving, A's own `AudioProcessorValueTreeState` timer runs at 50 Hz
    while values change, and brings A level with C.
- **Load, memory, size.**
  - Create time, each build described by its bundle: B 1.23 ms, C 2.11 ms, A and
    A-native 2.18 ms.
  - Private memory added: B 710 KiB, C 1,002 KiB, A 1,058 KiB.
  - Module size: B 428 KiB, C 6.3 MiB, A 7.1 MiB. C has no editor either, so most of the
    gap is JUCE's own modules, which every JUCE plugin links. A adds `juce_audio_utils`,
    `juce_dsp` and a generic editor on top.
- **Plugin code.**
  - A is 458 code lines of C++, or 335 without the 123-line port of Seam's ranges.
    A-native is built from the same source.
  - B and C share 501 lines of Rust. 140 of them are the biquad and its coefficient
    formulas, which A takes from JUCE's `dsp` module. rustfmt also spreads the parameter
    declarations over 190 lines, against A's 123.
  - Build lines: A's CMake target is 22, B's `Cargo.toml` 24, and C's 29 with its CMake
    call.
- **How firm.** This is one machine in one session. The spin tables are the firm ones;
  the idle figures at large blocks are not. The build order rotates each round, so no
  build is always measured first or last. The data for this run is in
  `2026-11-05-headless.json`, and the earlier idle-only run's is in
  `2026-11-05-headless-c84da6d.json`.

2026-11-05, Seam `6ca1cc2`, on AMD Ryzen 7 9850X3D 8-Core Processor (8 cores, 16 threads, 31 GB), Windows-11-10.0.26300-SP0.

## CPU while playing

Block times come from the processor's time stamp counter, which runs at a fixed 4.69 GHz here; a block's cycles in those units are its time times that rate. ## Load and memory

Every run is a fresh process that loads the build from a description naming its bundle, with no scan, as a host opening a project does: cold for the process, though the module's file is in the system's file cache from earlier runs. Create is `createInstanceFromDescription` (the bundle's search, the module's load, its factory and the instance); prepare is `prepareToPlay`. Memory is the host process's peak during the run less what it held just before creating the plugin.

## How it was measured

- Machine: AMD Ryzen 7 9850X3D 8-Core Processor; Power Scheme GUID: 8c5e7fda-e8bf-4a96-9a85-a6e23a8c635c  (High performance).
- Toolchains: rustc 1.99.1 (58cf8f9c3 2026-10-13); MSVC 19.44.35222.0; JUCE 9.0.0 (f8f8864).
- Builds: Release. Rust with fat LTO and one codegen unit; A, A-native and C with JUCE's recommended config and LTO flags (`/Ox /GL`, `-LTCG`), `/fp:precise`, and the dynamic C runtime; x86-64 with no CPU-specific flags on either side. MSVC's buffer security checks (`/GS`) are on, its default; Rust has no stack protector.
- The console host is `bench-hosted measure` (`bench/hosted/hosted.cpp`) on JUCE's VST3 hosting. One fresh process per run; 3 rounds, the build order rotating each round; per run 0.25 s of untimed warm-up, then at least 2 s and 1,000 blocks timed, stereo noise in, at 48000 Hz.
- The audio thread is MMCSS "Pro Audio" at time-critical priority, not pinned to a core, and starts each block when its frames would be due, spinning or sleeping on a high-resolution timer until then; the main thread runs the message loop. Only `processBlock` is timed, between fenced reads of the time stamp counter; it includes JUCE's hosting of the call, the same for every build.
- JUCE's hosting hands every build one buffer as both input and output. Seam's exporter processes it in place; JUCE's wrapper, in A, A-native and C, copies the input into its own buffer and the result back.
- The transport reports playing at 120 bpm, and every host write arrives in `process`, a value that moves what the parameter stores (bench/README.md, console host rules).
