# The ladder: from plain JUCE to Seam, one change at a time

The first report (`2026-11-05-headless.md`) found both Rust builds faster than plain
JUCE (A-native). This run asks why. A-native and C differ in three things at once: the
filter code, the compiler and the framework. Three more builds take that gap apart one
change at a time (bench/README.md, "The ladder"). The result: with the Rust EQ's own
filters in C++, built by LLVM, inside the same JUCE wrapper, plain JUCE is level with
Seam through that wrapper, or up to 3% faster. Seam's lead over A-native came from the
code JUCE's `dsp::IIR` puts around the filter loop, from MSVC, and, for Seam's own VST3
build (B), from its exporter. None of the three is the language. `scripts/compare.py`
made the tables below; this overview is written by hand.

## Overview

- **Output.** The port computes what the Rust EQ does: the parity tool on the port
  matches it in all 1,369,771 cases, built by MSVC and by clang-cl. A, B, C and C-clang
  play the parity script bit for bit through JUCE's hosting. In every timed run A, B, C
  and C-clang match each other bit for bit, and so do A-native, A-port and A-port-clang:
  324 comparisons, 236 million samples.
- **Each step, as a share of the time before it,** with the core awake, in every
  scenario, at 32 to 1,024 frames:
  - **port**, A-port against A-native, both MSVC: 0.92 to 0.95. JUCE's `dsp::IIR` runs
    the same arithmetic with more around it: an `AudioBlock` and a process context per
    call, a switch on the filter's order, a reference-counted coefficients object, 12
    calls a block against 6, and the coefficients normalised once per channel. This run
    does not say which of those costs what.
  - **compiler**, A-port-clang against A-port: 0.95 to 0.99, the most with every
    parameter moving.
  - **framework**, C-clang against A-port-clang, all LLVM inside the same clang-built
    wrapper: 1.00 to 1.03, so here the C++ is ahead. With every parameter moving at 32
    frames A-port-clang takes 2.76 µs against C-clang's 2.83; with nothing moving at
    1,024, 23.38 against 23.62. The step holds Seam's parameters against JUCE's
    `AudioProcessorValueTreeState`, the adapter, the call across the C interface, which
    no link-time optimisation inlines, and two LLVM versions compiling two sources; this
    run does not separate them.
  - **wrapper compiler**, C against C-clang: 0.96 to 1.02. MSVC's build of JUCE's
    wrapper and the adapter is level with clang-cl's, and 2 to 4% faster with every
    parameter moving at up to 256 frames.
  - **exporter**, B against C: 0.74 to 0.98, the one large step. Seam's VST3 exporter
    against JUCE's wrapper and the adapter takes 0.93 to 0.98 with nothing moving, 0.89
    to 0.97 with one parameter moving and 0.74 to 0.92 with all 18. It is widest at
    small blocks with parameters moving, so most of it comes per block and per write.
    With nothing moving it grows from 0.05 µs a block at 32 frames to 0.74 µs at 1,024,
    which the first report puts down to the wrapper's copies.
- **Against the fastest C++ here.** A-port-clang, plain JUCE with hand-written filters
  built by clang-cl, takes 0.89 to 0.93 of A-native's time. C takes 0.99 to 1.05 of
  A-port-clang's: level. B takes 0.94 to 0.99 of it with nothing moving and 0.73 to 0.96
  with every parameter moving.
- **The first report, read again.** It found C at 0.88 to 0.94 of A-native. Taken
  apart, JUCE's filter code is 5 to 8% of that, the compiler most of the rest, and
  Seam's framework gives back 0 to 3%. B's further lead is its exporter.
- **Load and size.** Create time: A-port-clang 2.07 ms and C-clang 2.00 ms, against
  2.21 and 2.14 for their MSVC builds. The clang-cl modules are about 1 MiB smaller
  (A-port-clang 4,973 KiB against A-port's 5,973; C-clang 4,978 against C's 6,280), and
  A-port's is 1.1 MiB smaller than A-native's. Outside `process`, C-clang's tick costs
  what C's does.
- **How firm.** One machine, one session, the spin pace only; the first report's idle
  figures at large blocks were noise. Outside busy at 1,024 frames, where every build
  took 4.5 to 7% longer than in the first report, the builds it measured repeat its
  times closely (median difference 0.3%). In most cells the three rounds lie within 3%
  of their median, or two of them do and the median holds. At 512 frames with
  parameters moving the rounds disagree by up to 29%, so the ranges above leave those
  two rows out. C-clang with every parameter moving at 1,024 frames is loose too (27.07
  to 29.65 µs). Each step's ratio is steady across the other block sizes. The data is
  in `2026-11-05-ladder.json`.

## How it was measured

- Machine: AMD Ryzen 7 9850X3D 8-Core Processor; Power Scheme GUID: 8c5e7fda-e8bf-4a96-9a85-a6e23a8c635c  (High performance).
- Toolchains: rustc 1.99.1 (58cf8f9c3 2026-10-13); MSVC 19.44.35222.0; clang-cl 22.1.6 with lld-link; JUCE 9.0.0 (f8f8864).
- Builds: Release. Rust with fat LTO and one codegen unit; the C++ with JUCE's recommended config and LTO flags, `/fp:precise` and the dynamic C runtime: under MSVC `/Ox /GL` and `-LTCG`, under clang-cl `/Ox`, which it takes as `-O3`, Rust's level, and `-flto`. x86-64 with no CPU-specific flags on any side, so no compiler can fuse a multiply-add. Both C++ compilers keep buffer security checks (`/GS`) on, their default; Rust has no stack protector.
- The console host is `bench-hosted measure` (`bench/hosted/hosted.cpp`) on JUCE's VST3 hosting. One fresh process per run; 3 rounds, the build order rotating each round; per run 0.25 s of untimed warm-up, then at least 2 s and 1,000 blocks timed, stereo noise in, at 48000 Hz.
- The audio thread is MMCSS "Pro Audio" at time-critical priority, not pinned to a core, and starts each block when its frames would be due, spinning or sleeping on a high-resolution timer until then; the main thread runs the message loop. Only `processBlock` is timed, between fenced reads of the time stamp counter; it includes JUCE's hosting of the call, the same for every build.
- JUCE's hosting hands every build one buffer as both input and output. Seam's exporter processes it in place; JUCE's wrapper, in every other build, copies the input into its own buffer and the result back.
- The transport reports playing at 120 bpm, and every host write arrives in `process`, a value that moves what the parameter stores (bench/README.md, console host rules).
